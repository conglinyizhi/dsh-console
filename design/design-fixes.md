# 设计清单修正（六条，按顺序做）

依据：ui-boot 包里的 ui-rules 与 checklist（2026-10-19 更新版）。每条都要在改完后用同一套量数复测。

## 1 状态灯补第二通道

问题：灰度下运行 0.416 与故障 0.431 几乎同一亮度，只靠颜色。
做法：总览卡片与配置侧栏的状态灯旁边补**文字状态**（运行 / 故障 / 已停止 / 试跑）。卡片高度最多 +2px；空间不够时把状态词放在第二行行首，与「上次启动 …」并列，格式 `运行中 · 上次启动 10-19 10:08`。
验收：灰度截图下三种状态可区分；文字状态在 DOM 里（data-state 旁边）。

## 2 中性灰补到 8 档

问题：现在实色中性灰只有 5 档，层级靠 alpha。
做法：在 SCSS 里立一组中性色阶（例如 `$gray-0 … $gray-7`，从页面底到最亮的文字），至少 8 档实色；页面底、面板、卡片、悬停、边框、次要文字、输入框底各取一档。少用 rgba 叠在白底上凑灰。
验收：量到的实色中性灰 ≥ 8 档；对比度不下降（低对比 0 条）。

## 3 空状态加行动号召

- 维护页空态：一颗 `开始一条作业`，点了把焦点送到「目标版本」那一格（或滚到表单）。
- 总览空态：一颗 `刷新读数`（现有动作）或把顶部「新建实例」的入口指出来，二选一，选能真点的那个。
验收：空态里有可点的按钮，点完有可见反应；按钮在灰度下也抢眼。

## 4 抽屉主按钮降一档

问题：抽屉里「启动」与「打开 Web UI」都是实心。
做法：「打开 Web UI」改次要样式（线框或低对比浅底），「启动」保持唯一实心；目标在跑时「打开 Web UI」成为主操作（那时没有「启动」）。一屏一个主操作。
验收：抽屉里实心按钮数在任一行状态下 ≤ 1。

## 5 1px 线减一轮

问题：总览 21 条、设置 28 条、关于 37 条 1px 线。
做法：优先用手上已有的灰阶（第 2 条）做底色差与留白分离；卡片与页面底之间、面板与卡片之间先删线；保留输入框、表头分隔、确认框边线。
验收：三类页面 1px 线条数各降三分之一以上（总览 ≤ 14、设置 ≤ 18、关于 ≤ 24），灰度下仍能分清区块。

## 6 关于页正文行高 1.7 → 1.8

验收：计算样式 line-height/font-size = 1.8。

## 20 「从基础实例开始」：没有可用配置时的备用入口

前提：现有 profile 全坏、或全不可用时，用户仍要能建一只新的。做法是用 dsh 自带的基础模板新建一份，不依赖任何现有配置。

### 20.1 后端

动作 `create-base-profile`，参数 `{"name":"<名字>"}`：

1. 名字按既有规则校验（单段、只允许字母数字与 . _ -），已存在报 conflict；
2. 用已安装的 dsh 跑：`node <包目录>/lib/bin.js --profile <名字> --from-default-profile web --dump-config`，
   DSH_HOME 用控制台的 home，超时 60 秒；成功后退出码 0 且不会留下进程（已实测：只写 profile，不启动）；
3. 核对：`profiles/<名字>/package.json` 读得出、bundles 里有 `@deepseek-ai/dsh-web-app`、`cordis.patch.yml` 在；
4. 默认隔离（复用既有 isolate_profile）；隔离失败不影响建成功，回执照实说；
5. 任一步失败：删掉刚建的 profile 目录，回 io-error 并带 stderr 尾部。

回执：`已从基础模板新建 <名字>（已隔离到 <路径>）`。

### 20.2 前端

在「新建实例」对话框左下角加一颗**不显眼**的入口：文本按钮 `从基础实例开始`（低对比、无边框、字号比正文小一档），与右下角的「创建 / 取消」分开。

- 点它：把源切成「基础模板」，名字默认 `base-<两位序号>`（已存在就顺延），焦点进名字格；
- 选中后，「创建」调用 `create-base-profile`，不再走派生；
- 悬停说明：`用 dsh 自带的基础模板新建一份，不依赖现有配置。现有配置都不可用时用这个。`
- 没有可用 profile 时，这颗入口照旧可见可用。

### 20.3 文案（待审）

- `从基础实例开始`
- `用 dsh 自带的基础模板新建一份，不依赖现有配置。现有配置都不可用时用这个。`
- `已从基础模板新建 <名字>（已隔离到 <路径>）`
- 回执照实的两支：`已从基础模板新建 <名字>（隔离 home 没建成：<原因>，它与别的 profile 共用 DSH_HOME）` / 失败时后端原话

### 20.4 验收

1. 临时环境里：没有可用 profile 时，对话框里只有这颗入口可用；点它 → 名字预填 → 创建 → 新 profile 出现且 `homeKind=isolated`
2. 新 profile 能起实例（临时环境里真起一只，等到签名通过）
3. 同名已存在时报 conflict；名字非法时报 bad-params
4. dsh 跑失败（把包目录指坏）时，刚建的目录不残留
## 21 新建实例：基础模板改成复选框

## 22 锁住源配置改成整片遮罩；note 去掉看不懂的那句

### 22.1 锁的方式换成祖先元素

勾上「从基础实例开始」时，不再给每张卡加 locked / aria-disabled / tabindex 那一套，改成：

- 源卡列表容器加 `inert`（整组不可聚焦、不响应事件）与 `aria-disabled="true"`；

- 列表保持原来的高度与滚动位置，不做隐藏与搬动；
- 勾掉：移除 inert 与遮罩，一切照旧。

卡片本身只保留读数带来的 `data-usable`，不再写 `data-selectable` / `data-locked`。

`create-base-profile` 的 note 里「没有留下进程」这句去掉，改成：

## 24 新建实例框三处：必填星号、卡片等高、勾选不再抖高度

### 24.1 名字是必填

- 标签「新实例名字（源配置：…）」前面加一个红色星号 `*`：`<span class="dsh-req">*</span>`，颜色用现成的 danger 色，`aria-hidden="true"`；输入框加 `aria-required="true"`，并在悬停里写「必填」。
- 星号不参与读屏报读（读屏靠 aria-required）。

### 24.2 源卡等高，原因只占一行

- 栅格里每张卡高度一致（`align-items: stretch`，行高由同一行最高决定但**每张卡都撑满**），卡片自身高度也钉死一档（例如 96px）。
- 不可用的卡：状态与缺包那一行照旧，原因那句（「这只配置起的是命令行型，没有网页入口」）**只占一行、超出用省略号**，完整句进悬停。
- 卡片内部纵向排布不留空洞：内容超出就裁，不许把卡撑高。

### 24.3 勾选复选框不许改对话框高度

- 名字格下面那句引导（「填一个名字，它会用基础模板新建」）改成**常驻占位**：没勾时这一行仍在，文字 `visibility: hidden`，高度不变。
- 勾上时列表上方的说明若也参与高度，同样改成常驻占位。
- 验收：勾上前后对话框总高度差 0；列表顶端与名字格顶端位置不动。

### 24.4 验收

1. 标签有红星号，输入框 aria-required=true
2. 1280 与 390 下所有源卡高度一致；不可用卡的原因只有一行并以省略号结尾，悬停里是完整句
3. 勾上 / 勾掉前后，对话框高度差 0，列表与名字格的位置差 0
4. 390 下同样成立；无横向滚动
## 25 配置卡片收敛成一个组件

问题（新建实例框截图）：列表里出现横向滚动条、卡片里「运行中 / 缺 6 个包 / 配置 home：共用」被折成两行、卡片塞的信息太多、框头那句说明随复选框切换变字。根子在于这张卡在四个地方各写一遍，改一处只修一处。

### 25.1 组件

在 `view_parts.mbt` 里做成一个组件（名字自定，例如 `profile_card`），四个地方全部改用它：

1. 新建实例框的源卡
2. 维护页「选择配置」（作业试跑）
3. 整体替换的选源列表
4. 维护页/其它地方若还有同款卡，一并收进来

组件入参：名字、备注（空则显示「没有备注」）、状态（运行中 / 已停止 / 故障 / 正在启动 / 状态未知）、状态原因、缺包数、配置 home 档（共用 / 独立 / 试跑 / 读不到）、不可用原因（可空）、标记（在跑 / 当前配置 / 已选 等）、点击回调、id 前缀、读屏标签。技术细节（home 路径、缺包名字、原因全文）只进悬停，不进正文。

### 25.2 卡片里显示什么

三行，固定高度 96px，一律单行省略：

1. 名字 + 状态词（状态词紧跟名字，同一行）
2. 备注（没有就写「没有备注」）
3. 缺包数 + 配置 home 档（两个短标记同一行）

不可用时第 3 行换成原因（单行省略，全文进悬停）。**不再显示**：缺包清单、home 路径、上次启动时间。

### 25.3 不许出现的排版问题

- 卡片内任何文字不换行：`white-space: nowrap` + 超长省略号；「运行中」「缺 6 个包」「配置 home：共用」这类短标记必须一行。
- 列表容器 `overflow-x: hidden`；卡片 `overflow: hidden`；任何一张卡的 `scrollWidth` 不得超过 `clientWidth`。
- **状态灯挂在图标右上角**（图标容器 `position: relative`，灯 `top: -3px; right: -3px`），不再相对整张卡定位，也不许溢出卡片。
- 四个调用点的卡片高度必须一致（96px），不允许某个页面被内容顶高。

### 25.4 框头那句固定

新建实例框的说明句不再随复选框换字，固定为：

`从现有的某个配置复制一个，或者是创建一个全新的`

复选框只影响卡片区锁不锁、名字格引导要不要显示，不改这一句。

### 25.5 验收

1. 新建实例框：列表无横向滚动条（`scrollWidth == clientWidth`），四张卡里没有任何文字折行，卡高全 96
2. 勾上 / 勾掉：框头那句文字完全不变
3. 状态灯在图标右上角，不溢出卡片（卡片 scrollWidth 不因它变大）
4. 维护页「选择配置」与整体替换选源：卡片结构、高度、悬停与改后一致；点选、禁用、当前配置标记照旧
5. 390 宽下三处都没有横向滚动，卡片仍单列
## 26 灯语义、卡片尺寸、对话框尺寸、悬停描边

### 26.1 灯四档，红灯只在真炸时亮

| 状态 | 灯 | 状态词 | 判据 |
| --- | --- | --- | --- |
| 运行中 | 绿 | 运行中 | 实例在跑 |
| 警告 | 黄 | 有警告 | 没在跑，或有在跑但 profile 有缺包等已知隐患 |
| 已停止 | 不显示灯 | 已停止 | 没在跑且没有警告 |

## 33 运行中实例来自别处 home 时，「配置 home」不该是「读不到」

现象（运行中的 renameme :8400，它的 home 是 /tmp/…，而控制台的 DSH_HOME 是 ~/.dsh）：
- 「配置 home」写「读不到」，紧接着「运行 home」却给出了 /tmp/… 的路径，两行互相打脸；
- 底下一句「这一版读数里没有「配置 home」，移进 / 移回都不发」——读数里其实有，只是这只 profile 不在控制台的 DSH_HOME 里；
- 插件数量、最近改动都是「—」。

根因：运行行先按「控制台的 profiles 读数」找这只 profile，找不到就判 home 未知；而实例自己的 home 明明读得到。

### 33.1 判据

- 运行行：先找 profile 读数（控制台 home 或隔离 home）；**找不到时用实例自己的 home**，来源写「按实例的 home 认定」。
- 「运行 home」这一行只在实例 home 与「配置 home」不同时才出现（现在这种情形两者相同，不该再单独出现）。
- 只有连实例 home 都认不出时，才写「读不到」并给缘由。

### 33.2 文案

- 实例来自别处 home、profile 不在控制台读数里时，配置 home 值写：`共用（<实例 home>）`，悬停 `按实例的 home 认定的：这只 profile 不在控制台的 DSH_HOME 里，所以按它跑着的那份 home 算`。
- 真认不出时：值 `读不到`，悬停 `这只实例的 home 与 profile 都认不出来（原因）`。
- 老后端缺字段时保留原句「这一版读数里没有「配置 home」…」。
- 插件数量、最近改动为「—」时悬停写 `这只 profile 不在控制台的 DSH_HOME 里，读不到它的这些读数`。

### 33.3 移进 / 移回

只有 profile 在控制台自己的 home（或隔离 home）里时才可用；否则按钮禁用，悬停 `这只 profile 不在控制台的 DSH_HOME 里，动不了它的 home`。

### 33.4 验收

1. 起一只 home 在别处的实例（控制台 home 不变）：配置 home 显示 `共用（<那份 home>）`，不再出现「运行 home」行，不再有「读数里没有这一项」那句
2. 同一场景下移进/移回禁用且悬停写清原因
3. 插件数量/最近改动「—」的悬停有解释
4. 正常场景（profile 就在控制台 home 里）行为与现在一致

## 37 临时环境（scratch）：控制台自己建、自己清（排队，等排期）

跨平台前提：不能依赖 /tmp 重启清空（Windows 的 %TEMP% 不保证清理）。由控制台自己管：
把 home 与 state 一起指到 `<scratch-root>/run-<启动时刻>-<pid>/`，重启时由控制台扫掉上次的残留。

### 37.1 形状

- 开关：`DSH_CONSOLE_SCRATCH=<root>`；给了就在启动早期把 home 与 state 指到该 root 下的一代目录。
- 一代目录里：`home/`、`state/`、`owner.json`（pid、启动时刻、版本）、`.lock`。
- 顺序：先写 `owner.json` 与 `.lock`，再建树；反过来会留下「目录在、没有主人」的残留。

### 37.2 清理（启动时，监听端口之前）

- 只认同时满足四条的目标：在 root 下、名字匹配 `run-<数字>-<数字>`、是目录、`owner.json` 可解析。
- 主人还活着（`/proc/<pid>` 的启动时刻与 owner 里一致，防 pid 复用）就跳过；死了才删。
- `.lock` 作为第二道：建好之前不删别人。
- 删前 realpath 校验，不跟随软链、不跨挂载点；失败只记一条 note，不挡启动。
- 正常退出顺手删自己那一份；异常退出留给下次启动扫。

### 37.3 与其它三种寿命区分

| 名字 | 寿命 | 谁清 |
| --- | --- | --- |
| `run-*`（本方案） | 一次控制台进程 | 控制台自己，启动时扫残留 |
| 隔离 home（按 profile 名） | 长期 | 用户手动移回 |
| `trial-*` | 一次作业 | 作业收尾时删 |

读数里的 homeKind 目前能表达隔离与试跑；scratch 要不要新增一档、前端文案怎么写，先对口径再动。

### 37.4 验收

1. 起一份：home/state 都在 run-* 下，实例的 DSH_HOME 指过去
2. `kill -9` 控制台再起：那份被清掉
3. 两份并存：谁也不删谁
4. root 里放一个不合规目录：一个字节都不动
5. Windows 语义下同样成立（逻辑不依赖 /proc 以外的系统特性；pid 存活判定要有跨平台实现或降级）
## 39 「缺 N 个包」给出自助修复

现状：profile 缺 bundles 时状态永远是「有警告」，用户只能自己进目录装包，界面只负责一直摆在
那儿报警 —— 报警不等于修复。

### 39.1 入口

抽屉「状态」组里，当警告的成因是缺包时，那句「缺 N 个包」下面多一行：

- 按钮 `安装缺的包`（线框、次要样式）；标签带数量：`安装缺的包（6）`
- 悬停：`在 <profile 目录> 里跑 <命令>；只动 node_modules，不改 package.json 与 cordis.patch.yml。输出写进 <日志路径>`
- 点它先开确认框（写 node_modules 算真动作）：
  - 标题 `给 <名> 安装缺的包`
  - 正文：`将在 <目录> 里执行 <命令>，只补 node_modules。装完会重新读一次这只 profile。`
  - 按钮 `安装` / `取消`

### 39.2 后端动作 repair-packages

参数：`{profile, home}`。步骤：

1. 校验目录与 package.json；目录不在就 `not-found`。
2. 选命令：有 `pnpm-lock.yaml` 用 `pnpm install --prefer-offline`；有 `package-lock.json` 用 `npm install --prefer-offline`；都没有用 `pnpm install --prefer-offline`。
3. 在 profile 目录里跑，120 秒上限；stdout/stderr 写进 `<state>/logs/repair-<profile>-<ms>.log`。
4. 跑完重新读这只 profile 的 bundles，算剩余缺包数。
5. 写审计（action `repair-packages`，outcome 带 command / exitCode / durationMs / logPath / missingBefore / missingAfter）。
6. 回执：成功且缺包为 0 → `<名> 的包已装齐`；仍有缺包 → `装了，但还缺 N 个（看日志）`，错误码 `install-incomplete`；命令失败 → 错误码 `install-failed`。
7. 同一只 profile 同时只允许一个修复在跑（第二个请求 `busy`）。

### 39.3 前端

- 修复中：按钮换成 `正在安装…` 并禁用；其余写动作按钮一起禁用（避免同时改配置）。
- 成功：提示条一句短的 + 读数自动刷新（灯应转绿或转回正常）；失败：提示条带「查看日志」按钮（§32 那条路），落到 `/logs/actions`。
- 失败原因完整原文进悬停与审计，不整段塞进提示条。

### 39.4 验收

1. 造一只缺包的 profile（临时环境）：状态「有警告」下出现 `安装缺的包（N）`
2. 点开确认框、确认：按钮变「正在安装…」，装完提示一句短的，读数重读后缺包为 0，灯不再是黄
3. 造一次失败（把 registry 指到不可达地址）：错误码 install-failed，提示条带「查看日志」，审计里有 logPath
4. 同时点两次只跑一个（第二次 busy）
5. 390 下确认框与按钮不溢出

## 48 搬家之后软链接断掉：relink

现象：`~/.dsh-homes/web-dev/profiles/web-dev/node_modules/@local/*` 里 13 个软链接全断
（`readlink -f` 给不出目标），而原 profile `~/.dsh/profiles/web` 的 13 个都正常。
插件列表于是把每个 `@local/dsh-*` 都标成「异常 / 包不可用」。

根因：这些链接是**相对路径**，例如 `dsh-annotate -> ../../../../../.pi/agent/.local-drafts/dsh-annotate`。
相对路径是从「链接自己所在目录」算起的。profile 被移到另一个深度的目录（隔离 home 多两层）之后，
同一段相对路径指到了别处 —— 目录移动（isolate / deisolate）与派生（fork）都只搬文件，没有重算这些链接。

### 48.1 搬家时重算

- isolate / deisolate 在移动之前先记下 profile 的旧绝对路径；移动之后走一遍 relink：
  - 只处理 profile 目录里的**符号链接**（含 node_modules 下）。
  - 对每个相对链接：用「旧链接所在目录 + 链接文本」算出它原本指向的绝对目标；
    再用「新链接所在目录」重新算相对路径写回。目标不存在就跳过（原本就是坏的，不猜）。
  - 绝对链接保持原样（它们不随目录变）。
- fork 照同一套做：从源 profile 复制完之后，按「源绝对路径 → 目标绝对路径」重算相对链接。

### 48.2 配置文件里的绝对路径

- `cordis.patch.yml` 与 `package.json` 里出现**旧 profile 目录的绝对路径**（例如
  `file://~/.dsh/profiles/web/node_modules/@local/dsh-linxi/lib/host.mjs`）时，
  搬家后把这些前缀换成新目录；只替换以旧目录开头的那一段，别的字符串不动。
- 替换条数写进审计 outcome（`refsRewritten`），没有就给 0。

### 48.3 已经坏了的那一份：不修

- **只做亡羊补牢**：已经断掉的那份（web-dev）不修，用户明确说现有那份不动。
- 不新增「修已存在坏链接」的后端动作，也不做任何猜目标的逻辑：坏链接在搬家时只是跳过。
- UI 里不加修复入口，文档里也不留修复引导（「移回再移出」那套已从本文档撤下）。

### 48.4 验收

1. 造一只带相对软链接的 profile（连同 `node_modules/@local/*`），isolate 之后：
   `readlink -f` 每个链接都能解析，插件列表不再是「包不可用」；deisolate 回来也一样
2. fork 到不同 home 深度的一份，链接同样可解析
3. 搬家后 `cordis.patch.yml` 里旧目录前缀被换掉，审计有 `refsRewritten`
4. 原本就坏的链接：搬家不把它修好，也不把它弄得更坏（跳过并记一条）
## 49 派生副本里还牵着外面的软链接：先告知

事实：有的 profile 里，`node_modules/@local/*` 是指向 profile 之外目录的软链接
（例如 `~/.pi/agent/.local-drafts/dsh-annotate`）。派生出副本之后，这些链接仍然指向**原处**：
在副本里改插件 = 改原处那一份，仍然会影响主机上的其他 profile。这叫藕断丝连。

### 49.1 读数里加一个数

- profiles 读数每只加 `externalLinks`：profile 目录内、解析之后落在**profile 目录之外**的软链接条数。
- 链接本身坏掉的（解析不到）不算进这个数，另用 `brokenLinks` 记数（不进 UI，供排查）。

### 49.2 派生时先问一句

- 抽屉「派生开发副本」：若 `externalLinks > 0`，先开确认框：
  - 标题 `派生 <名字> 的开发副本`
  - 正文：`这份副本里还有 N 个软链接指向原 profile 之外（例如 .pi/agent 下的本地插件）。`、
    `在副本里改这些插件，等于改原处那一份，仍然会影响主机上的其他 profile。`
    `要真正隔开，先把它们拷成实体文件再改。`
  - 按钮 `仍然派生` / `取消`
- `externalLinks == 0` 时照旧直接派生，不多一步。

### 49.3 派生完成后的回执

- 有外部链接时，提示里带一句短的：`（副本里还有 N 个软链接指向原处）`，详情进悬停。

### 49.4 文案（待审）

- `这份副本里还有 N 个软链接指向原 profile 之外（例如 .pi/agent 下的本地插件）。`
