变体 A 的理由 / 问题

  1. 「打开 Web UI」终于是它自己。运行中卡上最常按、最没有歧义的动作，恢复成一颗独立实心按钮：没有焊接的尖角，也就不会被读成「这个动作有变体」。
  2. 两个状态是同一个骨架。运行中 [打开 Web UI][停止][重启][⋯]、已停止 [▶ 启动][重启][⋯]——第一颗按钮语义相反、位置相同，重启 和 ⋯ 在两态里钉在同一处。使用者切状态时不需要重新找按钮，视线不跳。
  3. 收纳入口是独立点击目标。⋯ 是 30×30 的方形按钮，和左边任何一颗主按钮之间隔 6px，误触不会牵动主操作，主操作也不会顺手把菜单带出来。
  4. 代价：卡片右侧多一颗按钮的宽度（约 +36px）。已停止卡当前正是这个结构，所以真正变化的只有运行中卡，回归面小。
  5. 代价：⋯ 是纯图标，没有文字标签，第一次看到需要点一下才知道里面有什么。菜单第一屏应把高频项（查看日志 / 打开工作目录 / 编辑配置）放在易读位置。

变体 B 的理由 / 问题

合理之处（如实记）

「启动」确实是最像有变体的动作。如果将来出现「用别的来源启动这只 profile」「以 headless 模式启动」「换 DSH 版本启动」这类真实分支，启动按钮带尖角是说得通的——那时下拉装的是主按钮的同类变体，语义对齐。

但现在的问题

  1. 下拉里没有任何一个「启动变体」。当前菜单是 派生开发副本 / 归档 / 删除 / 查看日志 / 打开工作目录 / 编辑配置——全是与启动无关的其它操作。焊接的尖角承诺「这个动作有变体」，打开的却是别的东西，这是把「更多」挂错了位置。
  2. 两个状态反而更不一致。运行中卡第一颗是无尖角的纯按钮，已停止卡第一颗带尖角。同一个位置的同一颗主按钮，在两个状态下形状不同，使用者会以为「启动」比「打开 Web UI」多一层东西——实际上里面装的还是同一个收纳菜单。
  3. 已停止卡少了 ⋯，收纳入口变成了「启动的一部分」。想归档一只没在跑的 profile，得先点「启动」的尖角；运行中卡却是点行尾独立的 ⋯。同一个功能，两个状态两种找法。
  4. 误触面叠在不可逆动作上。尖角只有 26px 宽，和「启动」共用一条 30px 高的边；菜单里第三项就是删除。错手一次，代价比错开一个菜单大。
  5. 如果只按字面理解「已经把两段式挪到已停止卡」也算一种交代——它至少让运行中卡恢复干净。但比较基准是「两个状态一致」，那样只做了一半。
推荐：变体 A 两段式该拆掉、不该搬家——「更多」属于行尾的独立入口，不属于任何一颗主按钮；这样运行中与已停止是同一个骨架，只有第一颗按钮的语义随状态翻转。
